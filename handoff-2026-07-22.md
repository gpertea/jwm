## Flameshot on :1 (VNC) - dual-instance setup

Wanted: flameshot tray daemon + Ctrl+Alt+P capture on :1, while :0
keeps its own. Problem: flameshot is single-instance PER USER via two
mechanisms - a QLocalSocket guard with a hashed name under $TMPDIR,
and the org.flameshot.Flameshot name on the (shared) DBus session
bus. A plain `flameshot gui` on :1 silently delegated to the :0
daemon and captured the WRONG display (diagnosed via
`strace -e trace=connect`: connect to /tmp/<hash-base64>= socket).

Fix: ~/bin/flameshot-vnc wrapper - exports a private
TMPDIR=$XDG_RUNTIME_DIR/flameshot-vnc-tmp (defeats the local-socket
guard) and a private DBUS_SESSION_BUS_ADDRESS
(unix:path=$XDG_RUNTIME_DIR/flameshot-vnc-bus, dbus-daemon --fork
started on demand), then execs /usr/bin/flameshot "$@". Both the
daemon (StartupCommand) and the gui trigger must go through the
wrapper so they share the private TMPDIR/bus. ~/.jwmrc-vnc changes:
<Dock/> added to the tray (was absent - no systray before), a
StartupCommand for the wrapper, and Ctrl+Alt+P (mask="CA" key="P")
plus the old Super+Shift+S both bound to `flameshot-vnc gui`.
Verified: separate daemons per display, :1 capture geometry correct
(1735x971), icon docked. Known tradeoff: :1 flameshot notifications
go nowhere (no notification daemon on the private bus). Flameshot
config (~/.config/flameshot) is shared by both instances.

## Testing notes (hard-won, do not rediscover)

- VNC session on :1 runs its own `jwm -f ~/.jwmrc-vnc` - never pkill
  by bare "jwm" pattern.
- Xephyr dead space (outside Xinerama screens) keeps stale framebuffer
  garbage that looks like duplicated bars; xsetroot -solid before
  screenshots. Verify geometry with `xwininfo -root -tree`.
- Drive WM-mediated moves with `wmctrl -i -r <id> -e 0,x,y,-1,-1`
  (ids from wmctrl -l). xdotool windowmove bypasses the WM (moves the
  inner widget within the frame) - useless for testing migration.
- xterm titles get overwritten by shell prompts; use
  `xterm -T NAME -e sleep 1000` for stable labels in screenshots.
